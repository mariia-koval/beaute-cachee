# Beauté Cachée — Synthetic Sales / CRM, 2025

Полностью искусственная учебная база вымышленного премиального бренда. Не является выгрузкой реальной компании. Не связывать с реальными отзывами на уровне клиентов, заказов или товаров. Все имена сгенерированы; email используют example.com, телефоны — недействующие TEST-PHONE.

## С чего начать

Работайте с шестью файлами в `raw/`. CSV: UTF-8 с BOM, разделитель — запятая, десятичный знак — точка, пустая ячейка — отсутствующее значение. ID и телефоны импортировать как текст. Даты: YYYY-MM-DD HH:MM:SS. В pandas: `pd.read_csv('raw/customers.csv')`.

`reference/` — эталон для проверки после собственной очистки, не дополнительный источник для объединения. Внутри также журнал внесённых ошибок и результат проверки. `generate.py` воспроизводит данные с фиксированным seed, требует только Python 3 (стандартная библиотека). Запуск перезаписывает CSV.

После очистки: customers 5 000; products 200; orders 10 000; order_items 15 000; support_tickets 2 000; satisfaction_surveys 800. Всего 33 000. Исходные файлы содержат 111 дополнительных точных дубликатов. Прочие учебные ошибки: формат категорий, обязательные пропуски, неправильный порядок дат, оценка вне шкалы. Не все пропуски являются ошибками. Потерянные даты нельзя достоверно восстановить из raw: отмечайте их как неизвестные, не придумывайте значения.

## Связи и поля

- customers: `customer_id` — PK; `first_name`, `last_name` — имя и фамилия; `email`, `phone` — необязательные контакты; `customer_created_at` — создание CRM-карточки; `customer_creation_source` — Website Registration / Guest Checkout / Boutique; `country`, `city` — место проживания; `acquisition_channel` — Organic Search / Paid Social / Referral / Email / Direct; `email_marketing_consent` — Yes / No / Unknown. Канал привлечения отражает исторический источник, не текущее согласие на рассылку. 800 карточек без заказов; повторные имена не означают дубликаты людей.
- products: `product_id` — PK модели; `product_name` — название; `category` — Bras / Briefs / Bodysuits / Nightwear / Loungewear; `collection` — коллекция; `list_price` — каталожная цена единицы, EUR. Размерные варианты находятся в позициях заказа.
- orders: `order_id` — PK; `customer_id` — FK customers; `order_date` — оформление; `order_status` — Delivered / Shipped / Processing / Cancelled; `sales_channel` — Website / Boutique; `promised_delivery_date`, `actual_delivery_date` — обещанная и фактическая доставка. У бутиков и отменённых заказов доставка неприменима; у ещё не доставленных фактическая дата пуста.
- order_items: `order_item_id` — PK; `order_id` — FK orders; `product_id` — FK products; `size` — размер; `quantity` — число единиц; `unit_price` — цена единицы при покупке; `discount_amount` — скидка на ВСЮ позицию; `returned_quantity` — возвращённые единицы; `refund_amount` — возврат денег по ВСЕЙ позиции. Все денежные значения EUR, цены включают налоги, доставка исключена. Возвраты моделируются как завершённые к дате среза, на уровне целой позиции.
- support_tickets: `ticket_id` — PK; `customer_id` — FK customers; `order_id` — FK orders; `product_id` — FK products, необязательный, только товар в связанном заказе; `created_at`, `first_response_at`, `resolved_at` — создание, первый ответ человека, решение; `ticket_status` — Open / In Progress / Resolved; `contact_channel` — Email / Chat / Phone; `contact_reason` — Delivery / Size & Fit / Return & Refund / Product Quality / Other. В этой версии все обращения связаны с заказом. Пустая дата решения допустима для нерешённых обращений.
- satisfaction_surveys: `survey_id` — PK; `ticket_id` — уникальный FK support_tickets; `submitted_at` — ответ после решения; `csat_score` — целое 1–5. Отсутствие опроса не равно нулевой оценке.

Каждая FK-связь направлена от многих записей к одной родительской. Не объединяйте позиции заказов и обращения одним плоским join для расчёта сумм: это размножает строки. Сначала агрегируйте к нужному уровню.

## KPI — согласованные определения

Период заказов/обращений: 01.01–31.12.2025. Срез: 31.12.2025 23:59:59. Карточки клиентов могут быть созданы раньше. Даты в местном времени Europe/Paris без часового смещения; для компактного упражнения переходы DST не моделируются, SLA считается разностью записанных дат в календарных часах.

1. Total Revenue: сумма quantity × unit_price − discount_amount − refund_amount по неотменённым заказам. Возврат уменьшает исходный заказ; нет даты движения денег. Это условный net order value с налогами, не бухгалтерская выручка.
2. Number of Orders: уникальные order_id, кроме Cancelled.
3. AOV: Total Revenue / Number of Orders, включая полностью возвращённые неотменённые заказы.
4. Repeat Purchase Rate: покупатели с ≥2 неотменёнными заказами в выбранном периоде / покупатели с ≥1 таким заказом. Не lifetime retention.
5. Total Customers: уникальные карточки, созданные не позже выбранной даты; не число покупателей. Пропущенные даты raw учитывать отдельно как неизвестные.
6. Ticket Volume: уникальные обращения по created_at.
7. CSAT: оценки 4–5 / все допустимые ответы (1–5), по submitted_at. Product rating сюда не входит.
8. Average First Response Time: среднее (first_response_at − created_at), часы, среди обращений с допустимым ответом; период по created_at.
9. Average Resolution Time: среднее (resolved_at − created_at), часы, среди решённых; период по created_at. Нерешённые исключаются, что может смещать среднее.
10. SLA Compliance Rate: успешное завершение с первым ответом ≤12ч И решением ≤48ч / все обращения с определимым исходом на дату среза. Любое уже состоявшееся нарушение — fail, даже если обращение открыто. Открытое без ответа старше 12ч — fail; нерешённое старше 48ч — fail; ещё не просроченное и не решённое — pending, исключить из знаменателя. Пороги включительные. Некорректные даты raw сначала обработать как проблемы качества, не как SLA fail.

Для промежуточного среза скрывайте ответы, решения и опросы позже него. Статусы и возвраты отражают конец года: полноценные исторические снимки из этой версии не восстанавливаются.

## Смоделированные ситуации

Рост продаж и нагрузки в ноябре–декабре; больше задержек доставки в эти месяцы; повышенная частота возвратов и обращений по посадке у части моделей; возвраты денег требуют больше времени поддержки; при длительном решении чаще встречаются низкие оценки. Связи вероятностные, не доказанная причинность. Все выводы описывают симуляцию.

Структура намеренно компактна: нет платежей, складских остатков, истории согласий, отдельного справочника SKU и событий возвратов. Это аналитическая модель для портфолио, не production CRM.
